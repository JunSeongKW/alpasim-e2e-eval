# axe-v10 TensorRT 속도 측정 보고 (2026-10-02)

목적: axe-v10 모델에 TensorRT 를 적용했을 때 **추론 속도**가 얼마나 좋아지는가.
주행 점수 개선이 목적이 아니며, 점수는 "같은 모델인가" 확인용으로만 본다.

## 한 줄 결론

이미지 백본(ViT-S, 21.6M 파라미터)만 TensorRT FP16 엔진으로 바꿨을 때, 모델 1회 추론이
**단독 측정에서 58.1 → 41.0 ms(1.42배, 17.2 → 24.4 FPS)**, **시뮬레이터 안에서는
142.5 → 106.7 ms(1.34배, 7.0 → 9.4 FPS)** 로 빨라졌다. 8클립 모두 pass/fail 이 같았고
7클립은 점수까지 같았다. 대신 클립 1개의 총 소요 시간은 2% 만 줄었다. 로컬 구성에서는
렌더링이 병목이기 때문이다.

## 어디서 시간이 줄었나

모델 1회 추론(단독 58 ms)을 모듈별로 나누면 다음과 같다. hook 오버헤드 때문에 합계가
67 ms 로 실제보다 크게 잡히므로, 비율만 보면 된다.

| 모듈 | 시간 | 호출 수 |
|---|---:|---:|
| 이미지 백본 ViT-S (**TensorRT 적용 대상**) | 7.0 ms × 3 = 21.0 ms | 프레임 3장마다 1번 |
| BEV 인코더 (deformable attention, 순수 PyTorch) | 4.5 ms × 3 ≈ 13.5 ms | 프레임 3장마다 1번 |
| trajectory head | 11.6 ms | 1 |
| agent head | 9.3 ms | 1 |
| trajectory offset head (refinement) | 5.0 ms | 1 |

ViT 몫 21 ms 중 약 17 ms 가 줄었으므로, ViT 자체는 **약 21 ms → 4 ms (약 5배)** 로
빨라진 것으로 추정된다. 이 값은 직접 잰 것이 아니라 전체 차이에서 계산한 값이다. 나머지
약 40 ms(BEV 인코더·trajectory head·agent head)는 그대로 PyTorch FP32 로 돈다.

## 시뮬레이터 안에서 지연이 2.7배로 커지는 이유

단독 58 ms 인 모델이 시뮬레이터 안에서는 142 ms 가 된다. 로컬 구성에서는 한 GPU 에
드라이버 2개와 렌더러 2개가 같이 올라가 있어 GPU 를 나눠 쓰기 때문이다. 근거는 두 가지다.

- 최솟값이 단독 측정값과 같다: FP32 61 ms ≈ 58 ms, TensorRT 42 ms ≈ 41 ms.
- 경합은 두 쪽을 거의 같은 비율로 늘린다: p50 기준 속도 향상이 단독 1.43배, 시뮬레이터 안
  1.44배다. 그래서 줄어든 절대 시간은 경합 환경에서 더 크다(17 ms → 49 ms).

따라서 다른 환경으로 옮겨 쓸 수 있는 수치는 **배율(약 1.3–1.4배)** 이고, ms 절대값은
GPU 를 같이 쓰는 구성에 따라 달라진다.

## 기존 FP16 스위치와의 비교

드라이버에 이미 있는 `DRIVESUPRIM_USE_FP16=1`(PyTorch autocast)도 같이 쟀다.

| | 평균 | p50 | FP32 대비 |
|---|---:|---:|---:|
| FP32 | 58.1 ms | 57.6 ms | 1.00배 |
| FP16 autocast | 62.2 ms | 60.8 ms | **0.95배 (더 느림)** |
| TensorRT | 41.0 ms | 40.4 ms | 1.43배 |

ViT 는 설정(`bevformer_vits_amp=True`)에 의해 이미 bf16 으로 돌고 있다. 그래서 autocast 를
켜도 빨라질 부분은 없고 형 변환 비용만 늘어난다. 또 autocast 는 벤치 입력에서 선택
궤적을 바꿨다(최대 29 m). 반면 TensorRT 는 궤적을 바꾸지 않았다(0.0 m). 즉 이번 속도 향상은
"FP16 을 켠 효과"가 아니라 TensorRT 의 커널 융합과 최적화에서 나온 것이다.

## 측정 조건과 한계

- **클립**: `clips8.txt`. 직진·회전 × 한산·밀집의 4개 사분면에서 2개씩 골랐다. 클립당
  rollout 1회, 영상 끔.
- **구성**: 두 쪽 모두 axe-v10 그대로(같은 이미지·체크포인트, 리랭커 cache-centre-max γ=0.01,
  dev preset, MPC gains). 다른 것은 백본 교체 여부 하나뿐이다. FP32 는 GPU 0–3, TensorRT 는
  GPU 4–7 에서 돌렸고 카드는 모두 H100 80GB HBM3 이다. GPU 당 드라이버 2개와 렌더러 2개를
  올렸는데, 이는 공식 평가 배치와 다르다.
- **실행 시점**: 두 쪽이 거의 순차로 돌았다. FP32 는 19:12–19:23, TensorRT 는 19:21–19:31 로
  2분만 겹친다. 각 쪽은 자기 GPU 만 쓰므로 GPU 경합 조건은 같지만, CPU 부하는 완전히
  같지 않다.
- **준비 구간**: 드라이버마다 첫 3회 호출은 통계에서 빼고 따로 적었다.
- **단독 측정 입력**: 합성 입력이다. 지연은 텐서 shape 으로 정해지므로 시간 측정에는
  문제가 없다. 다만 궤적 일치 여부는 실제 클립 결과(위 점수 비교)로 판단한다.
- **로컬 시뮬레이터는 동기식**이다. 추론이 100 ms 를 넘어도 기다려 주므로 주행 결과는
  바뀌지 않는다. 공식 환경에 실시간 마감이 있는지는 이 측정으로 알 수 없다. 100 ms 는
  드라이버의 추론 주기(`DRIVESUPRIM_INFERENCE_INTERVAL_US=100000`)를 기준으로 삼은 참고선이다.
- TensorRT 가 torch 기본 스트림 위에서 돌아 "default stream" 경고가 난다. TensorRT 가
  동기화를 추가로 하고 있다는 뜻이어서, 별도 스트림을 쓰면 조금 더 줄일 여지가 있다.

## 제출 이미지에 넣으려면 (참고)

이번 측정은 TensorRT 를 이미지에 넣지 않고 호스트 디렉터리를 마운트해서 했다. 제출본에
넣으려면 다음이 필요하다.

1. TensorRT 런타임 라이브러리(약 3.2 GB)를 이미지에 넣는다. 런타임에는 `onnx` 가 필요 없다.
2. 엔진(`.plan`)은 같은 TensorRT 버전(10.13)과 같은 GPU 아키텍처(sm_90)에서 미리 빌드해
   COPY 한다. 공식 p5 H100 과 아키텍처가 같다.
3. `policy.py` 가 지금은 `/bench` 의 헬퍼를 import 하므로, 그 코드를 `drivesuprim_challenge`
   패키지 안으로 옮겨야 한다.
